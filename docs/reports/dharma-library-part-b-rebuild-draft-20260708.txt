1. DRAFT — corrected `--show-text` / "(no text)" documentation
   (fixes Claim A; replaces the "When to use" section)
================================================================================

Proposed replacement for the "When to use" section of SKILL.md:

---
## When to use
- `library-search --json` omits chunk text by default — pass `--show-text`
  to get it. Without the flag, a hit's JSON has no `text` key at all
  (renders as "(no text)" in some callers); this is a CLI default, not a
  data problem. Verified directly, repeatedly, against real chunks
  (Repetti, Capriles, general free-will queries): the same chunks that
  show "(no text)" without the flag return full, real text with it.
- Use `library-search --show-text` FIRST for most lookups — it's faster
  than the PDF fallback (no `pdftotext` round-trip) and the text is
  already there. Reach for this PDF-fallback skill when: `--show-text`
  output is too fragmentary to work with (chunk boundaries can cut
  mid-sentence), you need surrounding context beyond one chunk, or you
  need to search across the full text of a specific known book rather
  than semantic-search chunks of it.
- Also applies when: semantic search scores are low, results are
  off-topic, or a specific book was requested but not surfaced by
  `library-search` at all.

**Caveat, stated honestly:** every chunk checked in this and the prior
session's testing returned real text once `--show-text` was passed — no
genuinely-empty-payload chunk was found. That is not the same claim as "no
such chunk exists anywhere in the 1.1M-point collection" — a full audit of
the whole collection for genuinely empty `text` payloads has not been done
(the same scroll-timeout limits noted elsewhere in this skill apply). If a
specific chunk still shows no text WITH `--show-text` passed, that is a
real, different, worth-investigating case — don't assume it's the same
missing-flag issue.
---

Also removes the now-redundant standalone pitfall bullet ("library-search
--source <pdf> --chunk <N> flags do NOT work — they return empty output")
— verified false as *stated* in the earlier content review (those flags
don't exist in the script at all; invoking them errors rather than
returning empty output). Proposed replacement bullet for the Pitfalls
section:

---
- `library-search` has no `--source`/`--chunk` flags for retrieving a
  specific known chunk (checked directly against the script's argument
  parser — only `--category`, `--query`, `--subcategory`, `--tags`,
  `--estado`, `--language`, `--top`, `--show-text`, `--json` exist).
  Passing them errors out (unrecognized arguments), it does not silently
  return empty output. To pull a specific known chunk, use `--show-text`
  with a targeted `--query`, or fall back to `pdftotext` + `grep` on the
  known file.
---

# PDF Availability — Verified Against Both Library Locations

Last verified: 2026-07-08. Two independent facts, checked separately —
do not conflate them (this is the exact conflation that caused the
2026-07-07 incident):

1. Does a PDF file exist on disk for this book?
2. Is the book's text retrievable at all?

These are independent. A book can have real Qdrant chunk text (retrievable
via `library-search --show-text`) with NO pdf file, and the reverse is
never actually the issue in practice — if a PDF exists, `pdftotext` on it
always works.

**Two library locations exist — check both before concluding a PDF is
missing.** This is the specific mistake that produced a wrong "confirmed
missing" list on 2026-07-07: only `/opt/agents/library/buddhism/` (the
smaller, older, partially-synced mirror — ~93 originally-indexed texts
plus some newer additions) was checked. The actual live ingest source is
`/opt/calibre-web/library/` (~728 author folders — see `references/
qdrant-pipeline-architecture.md`). A book absent from the first location
is very often present in the second.

```bash
find /opt/agents/library/buddhism -iname "*<author-or-title>*" 2>/dev/null
find /opt/calibre-web/library -iname "*<author-or-title>*" 2>/dev/null
```

Only trust "the PDF is missing" if BOTH searches come back empty (or
backup-only in both).
